# عقد الحفظ الفعلي لأنشطة HTML — Backend API v1

> **الحالة (10 نوفمبر 2026):** تم تنفيذ **طبقة اتصال JS مغلقة افتراضيًا** واختبارها بمحاكاة Supabase. **لم تُنشأ دوال RPC أو جداول ولا ملفات Storage ولا عمليات كتابة في مشروع الإنتاج**، لأن مشروع `vkjkkezuyhhlcrxlvdbr` لا يظهر ضمن حساب Supabase المتصل حاليًا.

## الهدف

تحويل تجربة المعلم ← الفصل ← الطالب ← النتيجة من حالة مؤقتة إلى حالة محفوظة **بعد** الاطلاع على مخطط Supabase الحقيقي وإنشاء نسخة احتياطية واختبار RLS. يعتمد المشروع الحالي على جدول `classes`، و`students`، و`profiles`، و`lesson_files`، و`submissions` للأنشطة القديمة. لا نعيد بناء هذه الجداول ولا نغير نتائجها قبل فهم القيود والعلاقات الفعلية.

### ملفات الكود

- `assets/js/activity-persistence-adapter.js`: عميل JavaScript للدوال السبع المقترحة، ولا يفعل شيئًا عند تحميل الصفحة حتى يستدعيه التطبيق صراحة.
- `tests/activity-persistence-adapter.test.cjs`: اختبارات مستقلة بلا تبعيات خارجية، مع mock لخادم Supabase.
- `index.html`: يحمل الوحدة من أجل جاهزيتها المستقبلية، دون أي اتصال جديد بقاعدة البيانات.
- `assets/js/platform-config.js`: `activityPersistenceEnabled: false`؛ تظل القيمة غير مفعلة في الإنتاج إلى حين المراجعة.

**مهم:** قلب القيمة إلى `true` وحده لا يفعّل حفظًا آمنًا؛ يجب تركيب الدوال المصرح بها، وربط الواجهة بالعميل، والتحقق من قواعد قاعدة البيانات.

## 1. عقد الدوال المقترح — لم يُطبّق على الخادم

يرسل `supabase-js` الطلبات باستخدام جلسة المستخدم الحالية ومفتاح المتصفح العام، دون `service_role`.

| RPC المطلوب | المعاملات | النتيجة المتوقعة | التفويض الواجب على الخادم |
|---|---|---|---|
| `edu_activity_capabilities()` | بلا | `{api_version:"1.0", write_enabled:true}` | فقط للمستخدم المصادق؛ لا يدل وحده على صلاحية الإسناد |
| `edu_activity_publish(p_class_id, p_kind, p_title, p_html)` | فصل، نوع درس/واجب/اختبار، عنوان، HTML مستقل | `{assignment_id, status}` | مدير أو معلم يملك الفصل؛ فحص الحجم والنوع وحفظ خاص للملف وإصدار ثابت |
| `edu_activity_class_assignments(p_class_id)` | الفصل | قائمة تكليفات الفصل دون كشف إجابات الطلاب | مدير/معلم مصرح له بالفصل فقط |
| `edu_activity_my_assignments()` | **بلا student_id** | تكليفات الطالب الحالي | يستنتج الطالب وفصله من `auth.uid()` والربط الموثوق |
| `edu_activity_begin_attempt(p_assignment_id)` | التكليف | `{attempt_id, assignment_id, title, kind, html}` | الطالب صاحب التكليف فقط؛ إنشاء المحاولة خادميًا |
| `edu_activity_submit_attempt(p_attempt_id, p_event_id, p_kind, p_score, p_max_score)` | المحاولة، معرّف تكرار، نوع completed/result، درجات اختيارية | `{attempt_id, accepted, duplicate}` | ملكية المحاولة + صلاحيتها + منع التكرار خادميًا، وعدم قبول طالب مرسل من العميل |
| `edu_activity_class_results(p_assignment_id)` | التكليف | آخر محاولات ودرجات الطلاب المصرح بها | المعلم مالك الفصل أو مدير مصرح له |

**تنبيه:** هذه **تواقيع API مقترحة وليست أسماء دوال موجودة بالفعل**. نوع `p_class_id` والمفاتيح والعلاقات يُحدّد بعد فحص `classes.id` في المشروع الحقيقي. لا تنشئ Migration تخمينيًا يعتمد UUID أو Text قبل الفحص.

## 2. قواعد بيانات لازمة قبل التنفيذ

- كيان محمي للتكليف يربط **الفصل والمعلم ونوع النشاط والموعد والحالة وإصدار الملف**.
- حفظ HTML في محتوى خاص؛ لا يوضع في مستودع Git عام مع بيانات الطلاب، ولا في Bucket متاح للجميع.
- سجل محاولة يربط **التكليف والطالب ووقت الإنشاء والتسليم**. معرف الطالب يُستنتج خادميًا من الحساب، لا يُوثق بناءً على JSON من المتصفح.
- حقل درجة اختياري؛ يسمح بحالة `completed` بلا درجة، ولا يحولها إلى صفر.
- `UNIQUE(attempt_id,event_id)` أو آلية idempotency مكافئة لضمان عدم احتساب حدث واحد مرتين.
- الصفوف القديمة في `submissions` والملفات القديمة في `lesson_files` تظل كما هي.
- كل جدول متاح عبر Data API يجب أن يكون محميًا بسياسات RLS مع `GRANT` محدود. وظيفة `SECURITY DEFINER` ليست حلًا تلقائيًا؛ راجع الحاجة لها ومخاطر `EXECUTE` الافتراضية.
- إذا استُخدم أي `SECURITY DEFINER` فعليًا، يلزم تحقق يدوي من المستخدم، وتثبيت `search_path` وتأمين أذونات التنفيذ.

## 3. حدود الثقة

وصول رسالة `postMessage` سليمة من iframe يعني فقط أن **الملف نفسه أعلن الدرجة**؛ وهو ليس دليلًا ضد التلاعب من جهاز الطالب. لا يجوز وصف الدرجة بأنها مصححة خادميًا. عند إنشاء نتائج عالية الحساسية، نحتاج آلية تقييم أو تحقق مناسبة للمستوى المطلوب؛ دون فرض مصحح عام على جميع ملفات HTML.

`activityPersistenceEnabled` وعلامة `write_enabled` نقاط تهيئة، وليستا حماية أمنية. القرار النهائي بتنفيذ الكتابة يجب أن يتحقق **لكل RPC** باستخدام `auth.uid()` وفصل/محاولة موجودين وصلاحية خادمية؛ ولا يقبل حقل `role` أو `studentId` من المتصفح كدليل صلاحية.

## 4. تعاقد الواجهة مع العميل

```javascript
// مثال تطويري فقط: لا يُنفذ الآن على مشروع الإنتاج.
const client = window.supabase.createClient(supabaseUrl, publishableKey);
const activities = window.EduActivityPersistence.create(client, {
  enabled: window.EDU_PLATFORM.activityPersistenceEnabled === true
});
const readiness = await activities.probe();
if (!readiness.ready) {
  // أبقِ الواجهة التجريبية منفصلة، ولا تعرض تسليمات رسمية.
}
```

يفحص العميل أولًا `auth.getUser()` ثم `edu_activity_capabilities()` قبل كل نداء. وهو يتحقق من أنواع الحقول وحد HTML على العميل، لكن الخادم **يجب أن يعيد جميع عمليات التحقق**؛ حماية JavaScript وحدها غير كافية.

### استعمالات مخطط لها

```javascript
await activities.publish({classId,kind:"homework",title,html});
const mine = await activities.myAssignments();
const attempt = await activities.beginAttempt(assignmentId);
await activities.submitAttempt({
  attemptId: attempt.attempt_id,
  kind: "result",
  score: 2,
  maxScore: 2
});
```

لا تستقبل `submitAttempt` معرّف طالب. وحدث `completed` يُرسل بلا `score` أو `maxScore`. تحقّق الواجهة من `eventId` يسهل تتبع التكرار، لكنه لا يغني عن قيود خادمية.

## 6. قائمة اختبار إصدار الإنتاج

نجاح التطوير لا يتقرر من ظهور أزرار في الواجهة. قبل تفعيل الكتابة يلزم الاختبار على الخادم لما يلي: معلم فصل (أ) يحاول إسناد فصل (ب)، طالب يطلب تكليف طالب آخر، محاولة إرسال eventId مرتين، درجة غير صالحة، طالب خارج الفصل، إتمام دون درجة، حساب غير مفعل، ونسخة واجب قديمة قابلة للعرض.
