## 2. قواعد لا يُسمح بتجاوزها

1. لا SQL على الإنتاج ولا تحديثات دور/حذف/تعديل بيانات حية قبل الاطلاع على Schema/RLS/RPC ووضع خطة رجوع.
2. عدم تغيير المفاتيح الأساسية IDs الحالية أو مسح الجداول أو إعادة تسجيل الحسابات.
3. جميع الجداول والقيود الجديدة *إضافية/توافقية* بعد فحص الواقع، وليس إنشاءً افتراضيًا لأسماء مكررة.
4. `main` هو الإنتاج؛ كل مراجعة وتغيير يبدأ من فرع عمل مستقل.
5. أي ميزة واجهية تحتاج Backend غير موجود تُوسَم غير جاهزة، ولا تُقدَّم كميزة عاملة للطلاب.
6. الإعدادات العامة في الواجهة يمكن أن تحمل مفتاح Supabase `anon` فقط؛ مفاتيح الخدمة وقاعدة البيانات تظل أسرارًا خادمية.

## 3. جرد جداول مرجعي تمهيدي — يحتاج تحققًا من الخادم

| الموجود في JavaScript | الاستخدام القديم المرصود | الاتجاه المقترح بعد تدقيق المخطط |
|---|---|---|
| `profiles` | المستخدمون والأدوار وبيانات المعلمين | الاحتفاظ بالمعرفات، والتحقق من المدير الواحد وصلاحيات تحديث الأدوار |
| `classes` | الفصول وربط `teacher_id` | إضافة ربط مادة/دورة أو علاقة مناسبة، وعدم كسر ارتباط المعلم القديم |
| `students` | الطلاب وربط `class_id` وأكوادهم | حفظ الحسابات وطلاب الفصول القديمة؛ خطة دعم تعدد الفصول عند الحاجة |
| `lessons` | قائمة الدروس/الأنشطة الحالية | استخدامها كمكتبة محتوى أو إضافة نوع محتوى توافقية |
| `lesson_versions` | بصمة النسخة والأسئلة المستخدمة لتفسير المحاولات القديمة | الإبقاء للنتائج التاريخية والتمييز بين التقييم القديم والجديد |
| `lesson_files` | محتوى HTML وبصمة الملف | مواصلة دعم الرفع القديم ثم دراسة Supabase Storage تدريجيًا |
| `class_lessons` | إسناد الدرس للفصل | استخدامها أو توسيعها بعد فهم قيود التكرار والمواعيد |
| `submissions` | محاولات الطلاب ودرجاتهم القديمة | **لا مسح ولا تحويل صامت**؛ تمييز النتائج الجديدة عن التاريخية |

كيانات مقترحة من متطلبات المنتج — لا تُنشأ حتى التحقق من عدم وجود مكافئ: `subjects`، `courses` إن لزم، `class_sessions`، `attendance_records`، `activity_attempts` عند الحاجة، `audit_logs`، `platform_settings`، وعرض عام آمن للمواد المنشورة.

## 4. فحص قاعدة البيانات المطلوب قبل أول Migration

- جرد الجداول والأعمدة والأنواع وPK/FK وUnique وIndexes وTriggers وعدد السجلات.
- تفريغ تعريفات الـViews ودوال `setup_needed`, `attach_teacher`, `attach_student`, `submit_result`, `my_portal`, `my_homework` وصلاحيات `EXECUTE`.
- فحص سياسات RLS للجداول الحساسة، ودور كل من `anon` و`authenticated` وحدود كل معلم وطالب.
- تحديد طريقة إنشاء المدير الأول ومنع إنشاء مدير ثانٍ من جهة الخادم.
- جرد Buckets وStorage objects وربطها بالملفات؛ لا نفترض أن HTML الحالي موجود في Storage.
- تحديد اعتماد الصفحة على أي Edge Functions/Triggers/Cron غير محفوظة بالمستودع.
- تسجيل نسخة مرجعية لأعداد الفصول والطلاب والحسابات والدروس والنتائج قبل وبعد كل ترحيل.

## 5. النسخة الاحتياطية — مساران مختلفان

### أ. نسخة الكود — مُنجزة

- Snapshot code من `main` إلى فرع مستقل: https://github.com/arabicwithabdelmalek-cpu/nahw-dashboard/tree/backup/pre-platform-audit-2026-11-10
- هذه اللقطة لا تضم قاعدة البيانات أو إعدادات مصادقة Supabase أو محتويات Storage.
- إمكان العودة للكود: دمج/استرجاع commit المعروف بعد مراجعة العمل الجاري؛ لا تستخدم `reset --hard` أو `force push` تلقائيًا على الفرع المشترك.

### ب. قاعدة البيانات — **لم تُنفَّذ بعد**

توصي Supabase رسميًا بأخذ تصدير منطقي يدوي لمشروعات الخطة المجانية عبر CLI، إذ لا تتوفر لها نسخ تلقائية يومية. توثيق مرجعي:

- https://supabase.com/docs/guides/platform/backups
- https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore

بعد الدخول إلى **الحساب الثاني** والوصول للمشروع الصحيح، وعلى جهاز موثوق فقط:

1. تأكد من أن رابط الاتصال يأتي من لوحة **المشروع الصحيح** وليس من مشروع آخر.
2. ثبّت Supabase CLI حسب الوثائق، ثم راجع الصياغة الحالية بالأوامر `supabase --version` و`supabase db dump --help`.
3. احتفظ بسلسلة الاتصال في متغير بيئة محلي سري مثل `SUPABASE_DB_URL`، ولا تكتبها في مستودع عام أو محادثة.
4. نفّذ تصدير الأدوار والهيكل والبيانات في مجلد **خارج مستودع Git العام**، بعد التأكد من أن وجهة الملف صحيحة.

```bash
# أمثلة إرشادية من توثيق Supabase؛ تُراجع صياغتها عند التنفيذ.
# يشير SUPABASE_DB_URL إلى قاعدة مشروع النحو الواضح فقط.
supabase db dump --remote="$SUPABASE_DB_URL" -f roles.sql --role-only
supabase db dump --remote="$SUPABASE_DB_URL" -f schema.sql
supabase db dump --remote="$SUPABASE_DB_URL" -f data.sql --use-copy --data-only -x "storage.buckets_vectors" -x "storage.vector_indexes"
```

5. تحقق من وجود ملفات النسخ وأحجامها ومحتواها على نحو آمن، وخزنها مشفّرة في مكان منفصل.
6. وثّق ما يلزم حفظه خارج التفريغ: **كائنات Storage نفسها** (نسخة قاعدة البيانات تحفظ بياناتها الوصفية لا ملفاتها)، وEdge Functions، وإعدادات Auth/RLS الخاصة والخدمات.
7. **اختبر الاستعادة على مشروع مؤقت منفصل بعد موافقة صاحب المشروع**؛ لا تنفّذ استعادة على مشروع الإنتاج للتجربة.
8. لا تُعلَن النسخة «قابلة للاستعادة» حتى ينجح اختبار مستقل للهيكل والبيانات وسجلات الدخول/المرفقات بالحد المناسب.

**ممنوع:** رفع `roles.sql` و`schema.sql` و`data.sql` أو أي ملفات بها بيانات طلاب/اتصال إلى المستودع العام.

## 6. مراحل الترحيل المقترحة بعد اعتماد التدقيق

### المرحلة A — فصل الواجهة العامة عن منهج بعينه

- دعم اسم وهوية منصة قابلين للتهيئة، مع الاحتفاظ بكيان النحو الواضح كمقرر قائم.
- توثيق ما يمكن إنجازه بالواجهة وحدها وما يتطلب جداول إعدادات/مواد.
- عدم عرض بيانات خاصة على الواجهة العامة.

### المرحلة B — المواد والحصص والحضور

- إضافة جداول أو حقول توافقية بعد مراجعة العلاقات الحالية.
- ربط الجلسات بالفصل، وسجل حضور فريد للحصة/الطالب، مع وقت ومصدر التعديل.
- إبقاء الفصول والطلاب والنتائج القديمة كما هي، مع مفتاح تحويل واضح عند الحاجة.

### المرحلة C — تطوير HTML دون تدمير الصيغة القديمة

- دعم `lesson_files` الحالي بصورة آمنة؛ فصل طبقة رفع المحتوى العام (درس/واجب/اختبار) عن تحليل `CONFIG/TYPES/QUESTIONS` القديم.
- حفظ النسخة والبصمة، والاحتفاظ بمحتوى واجبات الطلاب التاريخي.
- تطبيق عارض HTML معزول وآلية رسائل موثقة، واختبار ملفات قديمة وجديدة قبل الاستبدال.
- عند النقل إلى Supabase Storage، يكون النقل بالتدرج والقراءة المزدوجة المؤقتة عند الحاجة، مع سجلات تحقق ومقارنة وليس حذف النسخة القديمة.

### المرحلة D — النتائج والحسابات وسجل النشاط

- استقبال نتائج HTML الجديدة خادميًا مع تأكيد ملكية المحاولة ومنع التكرار، دون بناء مصحح مركزي.
- دعم عرض نتائج `submissions` القديمة بجانب النتائج الجديدة؛ لا تحويل لدرجات قديمة دون موافقة.
- جعل إنشاء الحسابات وضبط الأدوار وإدارة «المدير الرئيسي الواحد» خادميًا مع RLS.
- سجل نشاط موثوق لا يقبل إدخالات وهمية من الواجهة.

## 7. خطة الرجوع عند حدوث مشكلة

- **واجهة فقط:** استرجاع commit معروف على فرع تطوير ثم اختبار، ومراجعة الدمج، من دون نسخ بيانات الإنتاج.
- **مخطط/بيانات:** تفضيل migration عكسي غير مدمر عند الإمكان؛ إذا كان الرجوع يعني استبدال بيانات، فلا ينفّذ قبل مراجعة أثره ونسخة حديثة واسترجاع تجريبي.
- **HTML:** إبقاء مسار العرض/القراءة القديم حتى نجاح اختبار العارض الجديد والملفات التاريخية.
- **حسابات الطلاب:** لا تغيير جماعي لمعرفات المستخدمين أو كلمات المرور. التراجع يُختبر بمستخدم تجريبي قبل أي نشر.
- **إيقاف العمل:** فور اختلاف العدادات الأساسية أو حدوث خرق صلاحيات أو فقد نتيجة قديمة أو عجز عن تسجيل الدخول.
