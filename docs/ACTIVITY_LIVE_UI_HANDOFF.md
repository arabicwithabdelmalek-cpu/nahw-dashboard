# توصيل الأنشطة المحفوظة بواجهات المدير والمعلم والطالب

> تاريخ العمل: 10 نوفمبر 2026. **واجهة جاهزة من جهة المتصفح، ومغلقة افتراضيًا. لا توجد دوال Supabase الفعلية ولا أي ترحيل لبيانات الإنتاج.**

## ما أُنجز

بُنيت واجهة مستقلة لمسار `#/activity-live` في ملف `assets/js/activity-live-ui.js`. تتصل عبر `assets/js/activity-persistence-adapter.js` الذي أُنشئ في الخطوة السابقة، باستخدام **نفس عميل Supabase الحالي** في `assets/js/app.js`، دون إنشاء عميل موازٍ أو وضع مفتاح خدمة في المتصفح.

عند توفر قاعدة البيانات والصلاحيات وتفعيل الميزة رسميًا، تعرض واجهة المعلم أو المدير:
- الفصول المسموح له بعرضها، وقائمة الأنشطة المسندة لكل فصل.
- نموذج إسناد HTML يحتوي الفصل ونوع النشاط (درس/واجب/اختبار) والعنوان والملف.
- نتائج كل نشاط كما تعيدها دالة الخادم؛ لا يتم عرض نتائج طلاب غير مسموح بها اعتمادًا على تصفية المتصفح وحدها.

تعرض واجهة الطالب:
- تكليفاته التي يعيدها الخادم وفق هوية الجلسة.
- زر بدء النشاط الذي يطلب محاولة من الخادم ويحصل على HTML المصرح به.
- عارضًا `iframe sandbox="allow-scripts"` معزولًا، ثم تسليم `completed` أو `result` إلى دالة الخادم.

### الفروق عن وضع المعاينة الحالي

| الخاصية | `#/activity-demo` | `#/activity-live` |
|---|---|---|
| الإتاحة | وضع `?demo=1` فقط | مقفل حاليًا بالإعداد `activityPersistenceEnabled:false` |
| مصدر البيانات | مصفوفات مؤقتة في المتصفح | دوال `edu_activity_*` في Supabase بعد تنفيذها |
| تخزين النتائج | لا يحفظ شيئًا | يتطلب تحققًا خادميًا قبل تأكيد الحفظ |
| هوية الطالب | نموذج تجريبي | `auth.getUser()`؛ والتفويض النهائي داخل RPC |
| تجربة النحو القديمة | لا تتغير | لا تتغير |

## ترتيب التفعيل الإجباري

1. فتح الوصول إلى مشروع Supabase الصحيح **`vkjkkezuyhhlcrxlvdbr`**؛ لا يظهر حاليًا في مشروعات الحساب المتصل.
2. تنفيذ `supabase/audit/`، وتوثيق أنواع المفاتيح والعلاقات وRLS والدوال الحالية.
3. حفظ نسخة احتياطية حقيقية من الجداول وStorage واختبار الاستعادة في بيئة منفصلة.
4. اعتماد تصميم الجداول والتراخيص ثم إنشاء migrations واختبارها خارج الإنتاج.
5. تنفيذ دوال RPC المتفق عليها في `docs/ACTIVITY_BACKEND_CONTRACT.md` مع تحقق الخادم من المستخدم والملكية وقيود التكرار.
6. اختبار عمليات الكتابة بحسابات وهمية معلم/طالب من فصلين مختلفين.
7. بعد نجاح كل البوابات فقط، تغيير `activityPersistenceEnabled` من `false` إلى `true` في `assets/js/platform-config.js`، ثم اختبار تسجيل تكليف ونتيجة حقيقيين على بيئة اختبار.
8. نشر التفعيل تدريجيًا بعد توثيق الرجوع، دون المساس بواجبات النحو السابقة.

**لا تغيّر القيمة إلى `true` الآن.** القيمة ليست آلية تفويض أمنية؛ دورها منع عرض وظائف غير جاهزة. لا بد أن ترفض كل RPC طلبًا غير مصرح به حتى عند محاولة استدعائه دون واجهة.

## عقد الاستجابة الذي تتوقعه الواجهة

الواجهة تتحقق من أن قوائم النتائج والتكليفات Arrays. هذه أمثلة **تصميمية مقترحة** وليست استجابة موثقة من قاعدة البيانات الحالية:

### `edu_activity_class_assignments(p_class_id)` / `edu_activity_my_assignments()`

```json
[
  {
    "assignment_id": "server-generated-id",
    "title": "تدريب الفاعل والمفعول به",
    "kind": "homework"
  }
]
```

### `edu_activity_begin_attempt(p_assignment_id)`

```json
{
  "attempt_id": "server-generated-attempt-id",
  "assignment_id": "server-assignment-id",
  "title": "تدريب الفاعل والمفعول به",
  "html": "<!doctype html><html lang=\"ar\">...</html>"
}
```

يُرجع الخادم `html` فقط إن كان الطالب مُسجلًا في الفصل ومصرحًا له بهذه النسخة من النشاط. لا يُمرَّر `student_id` من المتصفح إلى الدالة.

### `edu_activity_class_results(p_assignment_id)`

```json
[
  {
    "student_name": "طالب تجريبي",
    "status": "completed",
    "score": 2,
    "max_score": 2
  }
]
```

في حالة الإتمام بلا درجة تكون `score` و`max_score` قيمتي `null`، ولا تتحولان تلقائيًا إلى صفر.

### تأكيد الإرسال

`edu_activity_submit_attempt` يجب ألا يؤكد النجاح قبل حفظه خادميًا. عند التأكيد تظهر رسالة **«أكد الخادم حفظ التسليم»**، وعند فشل RPC تظهر رسالة خطأ واضحة. لا يجوز الاعتماد على الحدث الصادر من HTML وحده لإثبات حفظ الدرجة أو نزاهتها.

## حدود أمان مهمة

- لا ينشر المتصفح `service_role` أو سلسلة اتصال قاعدة البيانات.
- كل نشاط يُرسل بمعرّف تكليف، ولا يُقبل `student_id` أو `teacher_id` يختاره العميل لإثبات التفويض.
- يتم التحقق خادميًا من ملكية الفصل للمعلم، وربط الطالب بالفصل، ومدة صلاحية التكليف، ومصدر المحاولة وتكرار الحدث.
- المحتوى والعناوين المسترجعة من الخادم تُعرض بعد تحويل الأحرف الخاصة إلى نص آمن، لا بوصفها HTML موثوقًا.
- لا تُقرأ ملفات الأنشطة العامة دون تحقق؛ وينبغي اختبار المحتوى الكبير وإصدارات الملفات.
- يمكن تزوير نتيجة يصححها JavaScript في متصفح الطالب؛ تُعرض باعتبارها نتيجة ملف النشاط، لا تقييمًا غير قابل للتلاعب.
- تم الحفاظ على عارض النحو القديم دون تغيير ضمن هذه المرحلة؛ مخاطر عزل ملفات النحو التاريخية ما زالت تحتاج تدقيقًا مستقلاً.

## نتائج الاختبار المنفّذ

- **15 اختبار تكامل ناجحًا** لمحاكاة المسار الرسمي بخادم Supabase وهمي: العرض مع تشغيل/إيقاف الميزة، الإسناد، قائمة الطالب، بدء محاولة، تسليم درجة، تأكيد الحفظ، وعرض النتائج.
- **7 اختبارات واجهة قابلة لإعادة التشغيل** في `tests/activity-live-ui.test.cjs`، تشمل منع الإسناد لفصل غير مخول من الواجهة، وتجربة حساب الطالب، وتحويل النصوص غير الموثوقة إلى نص ظاهر وليس HTML.
- **10 اختبارات توافق ناجحة** لعارض HTML المعزول، تشمل استمرار عمل المعاينة التجريبية وعدم إعلان نجاح الحفظ الرسمي قبل استجابة الخادم.
- لا يوجد اختبار تسجيل حقيقي على قاعدة Supabase الثانية، ولا نعتبر نجاح المحاكاة بديلًا عنه.

**أمر الاختبارات محليًا** بعد تنزيل المستودع وتثبيت Node.js:

```bash
node --test tests/activity-persistence-adapter.test.cjs tests/activity-live-ui.test.cjs
```

**الخلاصة:** أكملنا ربط واجهات النظام الرسمي بخدمات Backend المتفق عليها من جهة الواجهة، ولم ننفذ Backend بعد. عدم إتاحة مشروع Supabase الصحيح لا يزال يمنع تشغيل الميزة على بيانات الطلاب.
